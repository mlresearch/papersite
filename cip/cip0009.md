# CIP-0009: pmlint posts — validate Jekyll `_posts` YAML on correction PRs

> **Note**: CIPs describe HOW to achieve requirements (WHAT).
> This CIP implements [REQ-0005](../requirements/req0005_post-yaml-edits-validated.md).

## Summary

Extend papersite linting so pull requests that edit published volume `_posts/*.md` (the FAQ correction path) are checked for:

1. Valid YAML / Jekyll frontmatter
2. Conformance to the paper frontmatter contract the theme expects
3. Within-post consistency between display fields and BibTeX-derived fields
4. Other known silent-failure classes (non-printables, bad UTF-8, broken `extras` shapes)

Compose this into `pmlint` as a **posts** mode (or automatic path when the volume is published), distinct from CIP-0008 intake lint — which correctly **skips** when `gh-pages` is present.

**Which requirements does this CIP address?** [REQ-0005](../requirements/req0005_post-yaml-edits-validated.md).

**Out of scope:** shipping the workflow file into every existing `vNNN`/`rNNN` repository (fleet rollout CIP after this is proven).

## Motivation

Published volumes tell editors to edit `_posts/` for citation corrections; BibTeX on the branch is often gone and does not drive the site. Today:

- `pmlint` (CIP-0008) exits 0 without checking once `gh-pages` exists
- The example volume workflow only runs intake `pmlint --check`
- Bad YAML or mismatched author/title fields can merge and break Pages or citeproc consumers (see CIP-0006 / v283, v316 class of bugs, discovered late)

We need a PR gate for the correction path that matches how people actually edit volumes.

Aligns with tenets: `data-integrity-over-convenience`, `automation-with-guardrails`, `reproducible-auditable-pipeline`.

## Detailed Description

### Relationship to CIP-0008

| Concern | CIP-0008 intake | This CIP (posts) |
|---------|-----------------|------------------|
| When | Pre-publication (no usable published site yet) | Published volume; PRs editing `_posts` |
| Primary inputs | `.bib` + PDFs at volume root | `_posts/*.md` (+ `_config.yml` when present) |
| Default on published repo | Skip (exit 0) | Run posts checks |
| `.bib` required | Yes | No |

Do **not** remove the published skip for intake mode. Add a clear second path so correction PRs are not silently unvalidated.

### Proposed CLI / composition

Prefer extending `bin/pmlint` rather than a parallel entrypoint:

```bash
# Explicit
pmlint posts --check              # all _posts in tree (or gh-pages checkout)
pmlint posts --check --changed    # only files changed in the PR (CI)

# Auto (optional v1 or v1.1): if volume_is_published && _posts present → posts mode
pmlint --check                    # intake when unpublished; posts when published
```

Implementation sketch:

1. Resolve volume dir / papersite root (reuse CIP-0008 resolution; self-update still applies)
2. Locate `_posts/` (working tree, or `gh-pages` ref when PR is against that branch)
3. For each target post: split frontmatter, `YAML.load`, collect errors
4. Run schema / consistency / integrity checks (below)
5. Summary + exit `0`/`1`; `--check` remains non-mutating

Optional later: `jekyll build --dry-run` (or `jekyll build` in CI) when Gemfile + config exist — valuable but heavier; keep as Phase 2 so v1 stays fast and Ruby/YAML-only where possible.

### Frontmatter contract (v1 checks)

Ground truth for keys the theme reads is documented in [CIP-0005](cip0005.md) and produced by `lib/mlresearch.rb` `extractpapers`. v1 should enforce at least:

| Check | Fail when |
|-------|-----------|
| YAML parse | Frontmatter missing/`---` broken; invalid YAML; non-UTF-8 / control chars in loaded strings |
| Required keys | Missing `layout`, `title`, `author`, `id` (and `pdf` for `inproceedings` / equivalent paper layouts) |
| `layout` | Not a known paper/volume layout the theme supports (start with `inproceedings`, `proceedings` / site layouts actually in use) |
| `author` shape | Not the citeproc-style list of `{family, given}` hashes the generator writes |
| `extras` | Present but not a list of `{label, link}` maps |
| URL fields | `pdf` / `software` / extras `link` empty or clearly non-URL when set |

Historical volumes may omit optional keys (`extras`, `software`); absence is OK, wrong *type* is not.

### Within-post BibTeX vs display consistency

Generated posts store both processed display fields and BibTeX snapshots, e.g. `author` (array) and `bibtex_author` (string), plus `title` / `tex_title` where present (`lib/mlresearch.rb`).

v1 consistency checks (no `.bib` required):

1. If `bibtex_author` is present, every family name in `author[]` should appear in `bibtex_author` (normalised: casefold, strip braces/backslashes as needed)
2. If `tex_title` (or equivalent) is present, detexed form should match `title` under the same normalisation the pipeline uses — or flag gross mismatch
3. Report file + field; do not auto-rewrite in `--check`

When `bibtex_author` / `tex_title` are absent (hand-written or very old posts), skip consistency and still run parse + schema + non-printable checks.

### Non-printables / encoding

Reuse the CIP-0006 idea at post level: reject non-printable / C0–C1 controls in string fields of loaded YAML. That catches the same class of corruption if someone pastes bad text into a post.

### PR / CI wiring

1. Extend or add a sibling to `.github/workflows/pmlint-volume-example.yml` so published volumes run **posts** checks on PRs that touch `_posts/**`
2. Document in root `README.md` and point FAQ editors at “run `pmlint posts --check` locally”
3. Keep intake workflow behaviour for unpublished volumes unchanged

Path filters example:

```yaml
on:
  pull_request:
    paths:
      - "_posts/**"
```

Checkout must see the posts branch content (`gh-pages` or whichever branch holds `_posts` for that volume).

### Fleet rollout

Enabling this on every existing volume repo is **not** part of this CIP. After fixtures + a few live correction PRs pass, open a separate CIP for bulk workflow install (dry-run, skip customised workflows, new-repo template default).

## Implementation Plan

1. **Design freeze in this CIP** (Proposed → Accepted): confirm CLI shape (`posts` subcommand vs auto mode), required-key set, and consistency rules for old volumes.
2. **Validator library**: e.g. `lib/check_posts.rb` (+ thin `bin/` or `pmlint` section) — parse, schema, consistency, non-printables; `--check` only in v1.
3. **Wire `pmlint`**: `pmlint posts --check` [/ `--changed`]; keep intake skip-on-published.
4. **Fixtures + tests**: good posts; broken YAML; bad `extras`; author/`bibtex_author` mismatch; control characters.
5. **CI example workflow**: path-filtered posts job; docs in README.
6. **Prove on real PRs**: run against a small set of historical `_posts` and at least one live correction PR before Accept→close and before fleet CIP.

## Backward Compatibility

- Intake `pmlint --check` behaviour unchanged (including skip when published)
- No change to post file format; validators only report
- Volume CI remains opt-in until fleet/template work lands
- Old posts missing optional BibTeX snapshot fields still pass if YAML + schema + integrity OK

## Testing Strategy

- Unit: YAML fixtures under `tests/` for each failure class
- Integration: `pmlint posts --check` on a fixture volume tree
- Manual: run on a recent published volume’s `gh-pages` `_posts` (expect mostly pass; triage false positives before making CI required)
- Regression: ensure intake path still skips published volumes without `--force`
