# CIP-0006: Self-validating volume builds

## Status

- [x] Proposed
- [ ] Accepted
- [ ] In Progress
- [ ] Implemented
- [ ] Closed
- [ ] Rejected
- [ ] Deferred

## Summary

A new central test, tests/python/test_citeproc_yaml.py, fetches the
site-wide proceedings.yaml index from mlresearch.github.io and then
fetches and parses every volume's assets/bib/citeproc.yaml (generated by
the mlresearch/jekyll-theme remote theme) to confirm each loads as valid
YAML.

On its first run it found two real, already-published data problems
(v283, v316), stray non-printable Unicode bytes that made those volumes
citeproc.yaml unparseable. Both have now been fixed directly on their
gh-pages branches (see the linked backlog bugs). This CIP proposes moving
that validation closer to each volume's own build, so problems are caught
before publication rather than discovered later centrally.

## Motivation

The central test only catches problems after a volume is live, has to
re-derive from the outside something the volume's own Jekyll build
already knows, is slow (about 330 live HTTP requests, ~2 minutes), and
has no natural home in CI since papersite does not build or deploy any
individual volume. Catching mojibake, stray control characters, and
similar conversion artifacts at build time would stop bad data reaching
proceedings.mlr.press in the first place, matching the data-integrity
tenet of catching bad output before publication.

Both bugs found were traced to the *submitted* BibTeX itself (confirmed
by inspecting v316's original .bib in git history: the raw 0x02 bytes
were already there before any papersite conversion ran). That reinforces
the case for a check that runs as part of accepting a volume, not just a
central after-the-fact scan.

## Detailed Description

There is no single volume template repository in the mlresearch GitHub
org (confirmed via the API: no repo has is_template set). Volume repos
are created ad hoc by create_volume.sh / lib/mlresearch.rb and given
remote_theme: mlresearch/jekyll-theme. The effective "template" is the
combination of:

1. mlresearch/jekyll-theme, which supplies the Liquid template that
   generates assets/bib/citeproc.yaml from site.posts at build time.
2. papersite's lib/mlresearch.rb, which writes the per-paper _posts/*.md
   files that feed that template at volume-creation time.
3. Each vNNN repo's own GitHub Pages build.

Three possible places for a self-check, earliest first:

- Option A: in papersite at volume-creation time, running a local Jekyll
  build (or a proxy of the citeproc.yaml Liquid logic) against the new
  _posts before anything is pushed. Earliest possible, but needs a local
  Jekyll build or a proxy that can drift from the real theme.
- Option B: in mlresearch/jekyll-theme or copied into each vNNN repo by
  create_volume.sh, as a GitHub Actions workflow that builds the site and
  validates the generated citeproc.yaml before merge/deploy. Closest to
  "self-testing the repo", but retrofitting ~330 existing repos would be
  impractical, so it would only cover new volumes going forward.
- Option C: centrally in papersite, as implemented today. Cheapest, no
  changes to the theme or existing repos, but only ever catches problems
  after publication.

These are not mutually exclusive. A plausible end state is Option C as a
standing regression net (already implemented) plus Option B for new
volumes, added to create_volume.sh so every volume created from now on
self-validates before its first deploy.

A cheaper, incremental version of Option A worth considering separately:
extend papersite's existing pre-publication checker (lib/check_volume.rb)
with a check that rejects non-printable control characters (outside
whitespace) in any BibTeX field before a volume is even converted to
_posts. This would have caught both v283 and v316 at review time, without
needing a Jekyll build at all.

## Implementation Plan

Proposed only, not yet accepted:

1. Decide scope: is Option B worth the ongoing maintenance of a workflow
   across every future volume repo, and should it live in the shared
   theme or be copied per volume by create_volume.sh? Separately, decide
   whether to add a control-character check to check_volume.rb regardless
   (cheap, catches this class of bug earliest).
2. If accepted, add a workflow (e.g.
   .github/workflows/validate-citeproc.yml) that builds the Jekyll site
   and validates _site/assets/bib/citeproc.yaml, and wire it into
   create_volume.sh.
3. If accepted, decide whether to backfill existing volumes or leave them
   covered only by the central test.

## Backward Compatibility

No impact on published volumes or URLs; only adds validation that blocks
genuinely broken output.

## Testing Strategy

tests/python/test_citeproc_yaml.py already exists as the regression net
and has already proven its value (2 real bugs found and fixed on first
run). Any per-volume workflow added under this CIP should be tested
against a known-good volume and a deliberately broken fixture (e.g. a
post with a stray control character) to confirm it fails closed.
