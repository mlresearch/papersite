# CIP-0006: Reject non-printable characters in check_volume.rb, at volume intake

## Status

- [x] Proposed
- [x] Accepted
- [x] In Progress
- [x] Implemented
- [x] Closed
- [ ] Rejected
- [ ] Deferred

## Summary

A new central test, `tests/python/test_citeproc_yaml.py`, fetches the
site-wide `proceedings.yaml` index from `mlresearch.github.io` and then
fetches and parses every volume's `assets/bib/citeproc.yaml` (generated
by the `mlresearch/jekyll-theme` remote theme) to confirm each one loads
as valid YAML. On its first run it found two real, already-published
data problems, `v283` and `v316`, both now fixed and pushed (see the
linked backlog bugs).

That test catches problems by downloading the finished, deployed
artifact. This CIP proposes the more direct fix: add a check to
`lib/check_volume.rb` — the script that already runs against a volume's
submitted BibTeX before it is accepted — that rejects non-printable
characters in text fields. That is the earliest point in the pipeline
where a human reviewer can catch this, and it stops the bad data from
ever being converted, pushed, or published in the first place.

## Motivation

Both bugs were traced, via git history, to the *original submitted*
`.bib` file, not to anything `papersite`'s conversion pipeline
introduced:

- **`v283`**: the source `.bib` already contained the byte sequence
  `C2 80 C2 9D` in the paper title. Decoded as UTF-8 this is two
  characters, `U+0080` and `U+009D` — classic mojibake. The correct
  closing curly quote `”` (`U+201D`) encodes in UTF-8 as `E2 80 9D`.
  Something in whatever tool the authors used dropped the leading `E2`
  and re-encoded the remaining two bytes (`80`, `9D`) individually as if
  they were Latin-1, producing `C2 80` and `C2 9D`. This is a plausible
  encoding-mismatch artifact from a word processor or copy-paste chain,
  and it long predates any PMLR tooling.
- **`v316`**: the source `.bib` already contained 115 raw `0x02` (STX)
  bytes across 27 papers' abstracts and titles, each one sitting exactly
  where a word had been hyphenated across a line-break in the original
  PDF. This is a common artifact of certain PDF-to-text extraction
  tools, again introduced before submission.

Checking the *deployed* `citeproc.yaml` (as the new central test does)
only ever discovers this after a volume is already live — the broken
feed has been served to every downstream consumer by the time anyone
notices. Checking the *submitted BibTeX*, as `lib/check_volume.rb`
already does for several other classes of malformed input (double
backslashes, escaped `\$`/`\{`/`\}`, non-ASCII keys, double-braced
`pages` fields, and so on), catches it before the volume is ever
converted or pushed — at the point a human is already reviewing the
submission. That is a better fit for this project's "data integrity over
convenience" tenet: validate before conversion, not after publication.

## Detailed Description

`lib/check_volume.rb` runs a fixed set of checks against a volume's
`.bib` file (see its own header comment for the current list) and
exits non-zero if any check fails, before a volume is accepted. It
already has the exact structure needed for one more check: read the raw
bib content, scan line-by-line (tracking the current BibTeX key for
attribution), and report `error`/`warn_msg`/`ok` per finding, in the same
style as `check_escaped_chars` or `check_double_backslashes`.

The new check, `check_non_printable_characters`, should:

1. Scan the raw bytes of the `.bib` file (not just `title`/`abstract`
   fields — `v316`'s corruption could in principle appear in any text
   field) for bytes in the ranges `0x00`–`0x08`, `0x0B`–`0x0C`,
   `0x0E`–`0x1F`, or `0x7F`–`0x9F`. These are the C0/C1 control ranges,
   excluding tab (`0x09`), newline (`0x0A`), and carriage return
   (`0x0D`), which are legitimate in a text file.
2. Report each occurrence with the current BibTeX key, line number, and
   the character's hex code point (e.g. `[brindise25a] line 3: found
   non-printable character U+0080 — check for mis-encoded Unicode
   (mojibake) or a stray extraction artifact`).
3. Treat this as an `error` (fails the check, blocks publication), not a
   `warn_msg`, since no legitimate PMLR submission field should ever
   contain a raw control character.
4. Not attempt to distinguish "should this become a hyphen or be
   deleted" (that judgement call, as seen fixing `v316`'s 115
   occurrences, needs a human). The check's job is only to force that
   review to happen before publication, not to auto-fix it.

This does not need multi-byte UTF-8 decoding to catch either bug: both
`v283`'s `C2 80`/`C2 9D` and `v316`'s raw `0x02` contain at least one
raw byte in the flagged ranges (`0x80`, `0x9D`, `0x02`), so a simple
byte-range scan over the raw file catches both without needing to reason
about UTF-8 validity at all.

## Implementation Plan

1. **Add the check** to `lib/check_volume.rb`:
   - New method `check_non_printable_characters(content)`, called from
     `run` alongside the existing checks.
   - Follow the existing per-line, per-key attribution pattern used by
     `check_escaped_chars`.
2. **Add fixtures**, following the process in `tests/README.md`
   ("Extracting a fixture from a real PR"):
   - `tests/fixtures/v283_original/` — extract the real `l4dc2025.bib`
     from `mlresearch/v283` at the pre-fix commit (`e457c05^`), containing
     the `brindise25a` mojibake title, plus a dummy `brindise25a.pdf`.
   - `tests/fixtures/v316_original/` — extract the real
     `compayl25_cleaned_clean.bib` from `mlresearch/v316` (pre-fix commit,
     the parent of `13dd4a4`), containing the 115 `0x02` occurrences,
     plus dummy PDFs for its 27 keys.
3. **Add assertions** in `tests/test_check_volume.sh`:
   - `assert_error` for both new fixtures, checking for the new error
     message text.
   - `assert_no_error` in the `clean_volume` fixture section, to guard
     against false positives on ordinary text.
4. **Run** `bash tests/test_check_volume.sh --verbose` to confirm all
   pass, including the two new fixtures.
5. **Document** the new check in the header comment list at the top of
   `lib/check_volume.rb` and in `tests/README.md`'s fixture table.

The central Python test (`tests/python/test_citeproc_yaml.py`) is kept
regardless, as a safety net for the roughly 330 volumes that predate this
check and for anything the new check doesn't anticipate.

## Backward Compatibility

No impact on already-published volumes. This only adds a new failure
mode to `check_volume.rb` for *future* submissions containing raw
control characters — which should never be legitimate PMLR content in
the first place, so no existing well-formed submission should be
affected.

## Testing Strategy

- Two new fixtures (`v283_original`, `v316_original`) reproducing the
  exact real-world bugs found by `tests/python/test_citeproc_yaml.py`,
  per the project's existing fixture-extraction convention.
- `assert_no_error` coverage in `clean_volume` to guard against false
  positives (e.g. making sure legitimate multi-byte UTF-8 characters like
  em dashes, en dashes, and apostrophes — which also contain bytes in the
  `0x80`–`0x9F` range as UTF-8 continuation bytes — are not flagged; the
  check operates on raw single bytes in the C0/C1 control ranges, and
  UTF-8 continuation bytes for characters like `—`/`–`/`’` are `0x80`–
  `0xBF`, which overlaps the C1 range `0x80`–`0x9F`, so this needs a real
  test to confirm the check doesn't produce false positives on ordinary
  multi-byte UTF-8 text. This may require decoding the file as UTF-8
  first and checking *decoded* code points rather than raw bytes, to
  correctly distinguish a legitimate `—` (`U+2014`, valid multi-byte
  UTF-8) from a raw `U+0080` control character (also encodable in
  multi-byte UTF-8, but never legitimate in body text). This detail
  needs to be resolved during implementation, not glossed over — the
  `single-cell`/`H&E-stained`/etc. false positives encountered while
  manually triaging `v316` are exactly this trap.
