# CIP-0007: Batched alphabetical deploy for large PMLR volumes

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved, ready to start work
- [x] In Progress - Actively being implemented
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

Extend `bin/deploy_volume.sh` so large volumes can be published as many small
commit+push batches keyed by the first letter of each paper id (`a`–`z`),
instead of one monolithic commit of thousands of PDFs and posts.

Default behaviour for small volumes stays the current single-commit path.
A `--batched` mode (or automatic threshold) deploys:

1. **Assets → `main` only**, letter by letter
2. **Jekyll scaffolding → `gh-pages` once** (`Gemfile`, `_config.yml`,
   `index.html`, volume `README.md`, PR template)
3. **Posts → `gh-pages` only**, letter by letter
4. **Cleanup** so `main` holds only `assets/` + `README.md`, and `gh-pages`
   holds no `assets/` and no `.bib` files

A `--dry-run` prints per-letter file counts and the chosen mode without
pushing.

## Motivation

ICML volume 306 (~6552 papers) cannot safely use today's deploy script:

- A single commit of thousands of PDFs times out or overwhelms GitHub
- Pushing posts onto `main` then deleting them wastes history and confuses
  the branch contract (`main` = assets; `gh-pages` = site)
- Manual letter loops worked but were error-prone (zsh vs bash `mapfile`,
  interactive `cp` prompts, piping through `head` stalling Ruby)

We need the same two-branch end state as small volumes, with an auditable,
resumable path for large ones. Aligns with tenets
`clean-branch-separation`, `automation-with-guardrails`, and
`reproducible-auditable-pipeline`.

## Detailed Description

### Current behaviour (`deploy_volume.sh`)

1. Stage everything (`_posts/`, `assets/`, bib, config, README) on `main`
2. One commit on `main`
3. Branch/switch to `gh-pages`, `git rm -r assets/`, push
4. Remove bib from `gh-pages`, push
5. Return to `main`, remove Jekyll + bib, push

This is correct for workshop-scale volumes (tens to a few hundred papers).
It is the wrong unit of work for conference-scale volumes.

### Target behaviour

```
create_volume.rb          # unchanged for this CIP: local git mv + posts
deploy_volume.sh [flags]  # owns all commits and pushes
```

**Flags (proposed):**

| Flag | Meaning |
|---|---|
| `--batched` | Force letter-batched deploy |
| `--batch-threshold N` | Auto-batch when `max(assets, posts) > N` (suggested default 500) |
| `--dry-run` | Print letter → counts and planned steps; no git writes/pushes |
| `--from-letter X` | Resume batched push from letter `X` (inclusive) |
| existing `SKIP_CONFIRM=1` | Keep non-interactive confirm skip |

**Letter keying:** first character of the paper filestub / PDF stem
(lowercase `a`–`z`). Same key for `assets/${letter}*/` and
`_posts/*-${letter}*.md` so asset and post batches stay aligned.

**Dry-run output (example):**

```
Volume 306 deploy plan
  assets: 6552
  posts:  6552
  mode:   batched (threshold 500)

  letter  assets  posts
  a         155    155
  b         220    220
  ...
  z         671    671

  steps:
    1. main:    commit+push assets a–z (26 pushes)
    2. gh-pages: scaffolding commit+push
    3. gh-pages: commit+push posts a–z (26 pushes)
    4. gh-pages: remove bib if present
    5. main:    remove any stray Jekyll; ensure volume README
```

**Branch invariants (must hold after success):**

| Branch | Must contain | Must not contain |
|---|---|---|
| `main` | `assets/`, volume `README.md` | `_posts/`, `Gemfile`, `_config.yml`, `index.html`, `.bib` |
| `gh-pages` | `_posts/`, `_config.yml`, `Gemfile`, `index.html`, volume `README.md` | `assets/`, `.bib` |

**Important lessons from v306 to encode in the script:**

1. **Never put posts on `main`.** Create/update `gh-pages` and add posts
   there directly. Temporary “everything on main then delete” is fine for
   small volumes; for batched mode it duplicates work and leaves noisy
   history.
2. **Assets only on `main`.** Letter-batch the renames/adds under
   `assets/`; push after each letter.
3. **Volume README on both branches.** After cleanup, `main` must not
   keep the proceedings *template* README. Copy/ensure the generated
   volume README (`# PMLR NNN`) on `main`.
4. **Non-interactive file copy.** Use `/bin/cp -f` for the PR template
   (macOS `cp` may prompt and abort under `set -e`).
5. **Resumability.** If letter `m` push fails, `--from-letter m` continues
   without redoing `a`–`l`.
6. **Progress output.** Print `=== letter: N files ===` and
   `OK letter` after each successful push (as in the manual v306 run).

### Boundary with CIP-000A (fleet)

Both CIPs touch “many git operations” and dry-run/resume, but they solve
different problems:

| | [CIP-0007](cip0007.md) (this CIP) | [CIP-000A](cip000A.md) |
|---|---|---|
| **Job** | Publish **one** volume’s assets/posts to `main` / `gh-pages` | Install papersite-owned **artifacts** into **many** volume repos |
| **Unit of work** | Letter-batched commits **inside** one checkout | Inventory → PR **across** the fleet |
| **Mutates** | Volume content branches (PDFs, `_posts`, cleanup) | Usually additive files (workflows, templates), via PR only |
| **Entrypoint** | `bin/deploy_volume.sh` (`--batched`, `--dry-run`, …) | `pmfleet` (or equivalent) `inventory` / `plan` / `apply` |
| **Success** | Branch invariants hold for that volume | Campaign `missing` cleared (or skipped/custom accounted) |

**Do not merge these designs.** Fleet must not become a second deploy
engine; batched deploy must not become a multi-repo PR roller.

**Allowed hand-off (later):** after 0007 lands, CIP-0004 Phase 3 may wrap
`deploy_volume.sh` in Actions. If that wrapper (or a thin helper script)
must exist *inside* volume repos, CIP-000A runs a **campaign** to
distribute it. The campaign copies files and opens PRs; it does not run
letter-batched publish. Sorting that campaign is deferred until 0007 is
Accepted/Implemented and Phase 3 is specified.

### Out of scope for this CIP

- Changing `create_volume.rb` PDF `git mv` behaviour (already incremental
  locally; staging/push is the deploy script’s job)
- CI/CD auto-deploy (CIP-0004); this CIP only improves the local deploy
  tool CI/CD would eventually call
- Fleet install of any deploy workflow/helper → CIP-000A campaign (see
  boundary above)
- Parallel letter pushes (keep serial for simpler failure handling)

### Alternatives considered

1. **Git LFS for PDFs** — reduces push size but changes hosting URLs and
   editor workflow; larger change than batching.
2. **Subtree / separate assets repo** — stronger separation, much more
   operational complexity.
3. **Always batch, even for tiny volumes** — 26 empty or tiny commits is
   noisy; threshold keeps small volumes simple.

## Implementation Plan

1. **Refactor `deploy_volume.sh` into phases with helpers**
   - `count_by_letter <path-glob>`
   - `commit_push_letter_assets <letter>`
   - `commit_push_letter_posts <letter>`
   - `ensure_volume_readme`
   - Parse new flags; preserve `SKIP_CONFIRM`

2. **Implement `--dry-run`**
   - No mutations; print counts and planned mode
   - Exit 0

3. **Implement batched path**
   - Assets → `main` by letter + push
   - Create/update `gh-pages` without bringing assets (or remove assets
     immediately if branched from `main`)
   - Scaffolding commit on `gh-pages`
   - Posts → `gh-pages` by letter + push
   - Remove bibs from `gh-pages`
   - Verify `main` has volume README and no Jekyll/posts

4. **Keep legacy path**
   - When under threshold and not `--batched`, retain today’s single-commit
     flow (optionally still verify README is the volume version)

5. **Docs**
   - Update root `README.md` deploy section
   - Update `.cursor/rules/publishing_workflow.mdc`
   - Note `--dry-run` before first large publish

6. **Smoke test**
   - Dry-run against a small fixture or a previous volume checkout
   - Manual dry-run on a large volume directory if available

## Backward Compatibility

- Default without flags: if under threshold, behaviour matches today’s
  script (aside from the volume-README guard if we add it to both paths)
- Explicit `--batched` or crossing the threshold opts into the new path
- Existing `SKIP_CONFIRM=1` continues to work
- Volume editors who never pass flags see no change for small workshops

## Testing Strategy

- Unit-level: shell helpers for letter counting on a temp tree with known
  `assets/a*`, `assets/b*`, `_posts/*-a*.md` fixtures (bats if present,
  otherwise a small script under `tests/`)
- Dry-run on v306-scale paths should report 6552/6552 and 26 letters
  without network
- Integration: dry-run + `--from-letter` parsing; do not auto-push in CI
- Manual: one small volume via legacy path; one dry-run on a large volume
  before any real batched publish
