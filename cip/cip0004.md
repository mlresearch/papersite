# CIP-0004: Continuous Integration and Deployment for PMLR Proceedings

> **Umbrella CIP.** This document tracks the end-to-end publication automation
> roadmap. Concrete design and implementation live in child CIPs. Do not Accept
> this CIP as a single coding spike; Accept (or close) children as their phases
> land, and keep this document as the map.

- [ ] Implemented - Work complete, awaiting verification

## Summary

Automate PMLR volume publication so intake validation, compilation, and
deployment are repeatable and guarded, while editors retain a manual fallback.

| Phase | Outcome | Owns the HOW |
|---|---|---|
| 1. Intake validation | PRs to unpublished volumes fail on bad BibTeX / missing PDFs | **Done** — [CIP-0008](cip0008.md) (`pmlint`) |
| 2. Auto-compilation | Valid intake can produce a reviewable Jekyll tree (artifact or branch) without a local toolchain | *Open* — design stays here until a compile CIP is split out |
| 3. Deploy automation | Production publish uses the same branch invariants as today, including large volumes | Local batched deploy: [CIP-0007](cip0007.md); Actions wrapper later (this CIP) |
| — | Post-publication `_posts` YAML on correction PRs | **Out of scope** — [CIP-0009](cip0009.md) (Closed) |
| — | Rolling volume-local workflows / templates across the fleet | **Out of scope** — [CIP-000A](cip000A.md) |

Phase 1 deliberately skips published volumes (`gh-pages` present). That boundary
is correct for intake; do not overload intake lint for FAQ-style `_posts` edits.

## Motivation

Publication still depends on a long manual chain: clone → date BibTeX → tidy →
fix Unicode → `create_volume.rb` → `deploy_volume.sh` → verify Pages. That is
slow, easy to mis-order, and hard for new proceedings editors.

Automation should catch intake faults early, make compile/deploy auditable, and
keep scripts runnable outside Actions.

**Tenets:** `automation-with-guardrails`, `reproducible-auditable-pipeline`,
`clean-branch-separation`.

## Detailed Description

### Building blocks (already in papersite)

- `lib/tidy_bibtex.rb`, `lib/create_volume.rb`, `bin/deploy_volume.sh`
- `bin/pmlint` / `bin/pmlint-posts` (CIP-0008 / CIP-0009)
- Example workflows under `.github/workflows/`
- Unicode path via [CIP-0001](cip0001.md) + `unicode_replacements.yml` (not a
  separate phase of this CIP)

### Phase 1 — Intake validation (complete)

Implemented by [CIP-0008](cip0008.md):

- `pmlint --check` / `--fix` composing tidy + volume file checks
- Opt-in example PR workflow for volume repos
- Optional follow-ons (PR comment bot, default-on install) are fleet concerns →
  [CIP-000A](cip000A.md), not reopen Phase 1 here

### Phase 2 — Auto-compilation (open)

Desired outcome: from a valid unpublished volume tree, CI (or a one-command
local path CI mirrors) runs tidy + `create_volume.rb` and produces a reviewable
artifact or staging branch.

**Not decided yet (blockers for a child CIP):**

- Trigger: merge to `main`, workflow_dispatch only, or both
- Output: Actions artifact vs staging branch vs PR back to the volume
- Whether published date is injected automatically or supplied as an input
- Permissions and which repos may run compile

Until those choices are written down (here or in a split CIP), Phase 2 stays
Proposed design only — no backlog tasks.

### Phase 3 — Deploy automation (open; depends on CIP-0007)

Desired outcome: production publish is a guarded workflow (or documented
invocation) that ends in the same branch contract as a successful local deploy:

| Branch | Must contain | Must not contain |
|---|---|---|
| `main` | `assets/`, volume `README.md` | `_posts/`, Jekyll scaffolding, `.bib` |
| `gh-pages` | `_posts/`, Jekyll scaffolding, volume `README.md` | `assets/`, `.bib` |

**Hard dependency:** [CIP-0007](cip0007.md) owns batched/resumable
`deploy_volume.sh` for conference-scale volumes. Phase 3 must **call** that
script (with `--dry-run` / approval gates), not re-port deploy logic into YAML.

Actions wrapper concerns (after 0007 lands): secrets, environment approval,
post-deploy Pages check, audit trail. Overlap with fleet install of any
deploy workflow is sorted later with [CIP-000A](cip000A.md).

### Explicitly out of scope

- Post YAML lint for published volumes → CIP-0009
- Fleet distribution of workflows/templates → CIP-000A
- Unicode mapping DB / auto-PR for new characters → stay with tidy / CIP-0001;
  improve there if needed
- Editor dashboards, OpenReview import, bulk multi-repo orchestration → future
  ideas, not phases of this CIP

## Implementation Plan

1. **Keep Phase 1 closed** — track intake follow-ons under CIP-0008 / CIP-000A.
2. **Land CIP-0007** — batched local deploy with dry-run and branch invariants.
3. **Specify Phase 2** — resolve trigger/output/date/permissions; split a
   compile CIP if the design grows past a short section here.
4. **Specify Phase 3** — thin Actions (or documented) wrapper around
   `deploy_volume.sh` from CIP-0007; fleet install questions → CIP-000A.
5. **Close this umbrella** when Phases 2–3 are Implemented/Closed in their
   owning CIPs (or mark Deferred if compile/deploy-in-Actions is postponed).

## Backward Compatibility

- Manual `tidy_bibtex` / `create_volume` / `deploy_volume` remain supported
- Volume repo layout unchanged
- Workflows stay opt-in until fleet policy (CIP-000A) says otherwise

## Testing Strategy

- Phase 1: covered by CIP-0008 tests and volume example workflow
- Phase 2: fixture volume → artifact/staging matches local `create_volume.rb`
- Phase 3: dry-run deploy in CI; no unattended production push without approval;
  regression against small-volume legacy path and large-volume batched path
  (CIP-0007)

## Risks and Mitigation

1. **Auto-deploy mistakes** — dry-run, environment approval, call CIP-0007
   rather than a second deploy implementation
2. **False confidence from intake-only lint** — keep the gh-pages skip; use
   CIP-0009 for published-volume corrections
3. **Umbrella thrash** — do not open backlog under this CIP until a phase is
   Accepted with a clear owning child (or a short in-document design)

## Success Criteria

1. **Intake:** actionable check failures in minutes on unpublished volume PRs
   (met via CIP-0008)
2. **Compile:** valid intake yields the same tree a local `create_volume.rb`
   would, as a reviewable artifact or branch
3. **Deploy:** production publish matches manual branch invariants; large
   volumes use batched deploy; failed publishes are resumable or rolled back
   without hand-editing history
